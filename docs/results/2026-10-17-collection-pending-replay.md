# Private collection transaction and replay seam

This source-only store change prepares the approved authenticated collection entry. It creates no schema, public MCP tool, consent record, Google request, production deployment or matching input. The HTTP/factory `collect` integration awaits the Cloud owner's canonical action extension; existing owner/source contract bytes are unchanged here.

`ProfileSuggestions.propose` accepts an optional internal collection claim naming the batch UUID, existing signed inbound turn and raw request digest. It locks the canonical person/member, rechecks trusted owner and exact source authorization in that same transaction, and requires the completed OPEN parent to belong to the same person/app/member with the exact stored human command `collect <batch UUID>` and a retained signed request hash.

Pending rows and an action receipt commit together. The receipt uses the existing canonical envelope `{state: completed, requestHash, response}` and contains only input/request hashes and the batch ID. It includes no suggestion text. Existing action limits apply. Concurrent identical retries return the original pending batch. Changed input, another request hash, foreign owner, revoked permission or resolved/edited suggestions deny. The receipt survives batch deletion, preventing replay from recreating deleted content; a later turn cannot reuse its recorded batch UUID. If the signed inbound parent is purged, it cannot authorize replay. The UUID alone never establishes identity or permission.

Replay reads the already-owned batch directly under its lock after source authorization. It does not rebind owner identity and reset the source deadline. Fresh transaction authority and pending expiry fences run before writes and after the final read. A failure rolls pending rows and receipt back together. Only subsequent exact per-fact review can promote inferred facts into the canonical facet table.

Validation: pinned Bun 1.4.2 with isolated real PostgreSQL on port 54428. The initial combined focused suite passed 48 tests and 617 assertions. After the final review corrections, five collection-focused tests passed 36 assertions, and TypeScript passed. Independent review found and then verified fixes for the completed-receipt envelope and replay source-deadline preservation. Cases cover concurrent exact replay, changed/foreign inputs, revoke, unsigned/missing/handled parents, wrong human text, deletion/withdrawal/edit/reject replay, later-turn UUID reuse, atomic rollback and one owner/source binding per replay.

These fixtures control the trusted owner/source authorization seams. They do not prove the not-yet-wired collect HTTP route, real consent persistence, actual Google collection or live iMessage acceptance. The next receipt must join the canonical Cloud `collect` action and source proof to this store transaction without widening identity or source scope.
